### "1.100 FLS preparation" [fls#736](https://github.com/rust-lang/fls/issues/736)

Hristian: Do we have any release notes or anything to guide us?

Tshepang: Let me check. Here's the issue: https://github.com/rust-lang/rust/issues/163811

Pete: I'll use an LLM agent to analyze this issue and pull together a summary for us as Markdown. And then I'll post it under the FLS issue.

Tshepang: Pete, you said something was missing?

Pete: I thought there might be outstanding PRs for the Reference to document these things that are being stabilized.

(TC joined.)

Pete: (Explains the above to TC.)

Tshepang: In the list, it looks like we'll only care about 2 issues, the never type and external custom allocators.

Pete: TC, what do you think about how large these things are to document in the Reference, and have they landed? I recall there being some PRs for them.

TC: On the never type itself, it depends how you want to look at it. In one sense, documenting the never type (`!`) itself is a small change because it was already in Rust: when you write a function that returns `!`, it's there. We just didn't allow you to write it anywhere else. Now we do. But, because we do, that puts a lot of pressure on documenting divergence correctly, and the various behaviors of `!` correctly, because it's going to be more obvious to people what these are. And so the specific change for `!` is fairly modest, but the changes we've been making to document divergence and the behaviors related to `!` correctly have been extensive and are ongoing.

Hristian: TC, I assume these catchups aren't linked to the stabilization PR for the never type (!), and are done on the side?

(Tshepang shares https://github.com/rust-lang/reference/pull/2186 in chat for adding chapter in Divergence.)

TC: I have to look how we did it. The one for the stabilization would at least have gone through and fixed everywhere that we'd worked around the absence of `!` in our rules and examples.

Hristian: I found the original stabilization PR to be miniscule, and Tshepang just showed one that changes a lot of stuff.

Tshepang: TC, you're referring to...

TC: ...the `more-divergence` branch.

Never-type-related PRs:

- [Merged: Add a chapter on divergence](https://github.com/rust-lang/reference/pull/2067)
- [Add more rules about when expressions diverge](https://github.com/rust-lang/reference/pull/2186)
- [Merged: Update for stabilization of the never type](https://github.com/rust-lang/reference/pull/2283)

Hristian: The "Add more rules" one basically touches almost everything.

Pete: It seems I will need to point the agent at the above items as well, related to divergence. My summary of this, it appears there's more fundamental work that's been going for some time in the Reference, that likely didn't happen in the FLS, and `!` would now expose gaps in the FLS.

Hristian: Yes. We have many holes.

Pete: TC, is that accurate from your POV? The fact that there was a good deal of divergence work that has landed and is continuing to happen, and that there's not corresponding work in the FLS; and the never type landing exposing more gaps in the FLS.

TC: You would know better, but this sounds likely to me.

Hristian: There's no way this is not a hard "yes". The FLS has been lagging ever since 1.77.2, basically.

Tshepang: TC, for the open PR ("Add more rules..."), what's the status of it for it to be accepted? I see activity from 2 days ago.

TC: We work on it every single week, for hours.

Tshepang: Is it far from merging?

TC: Another two months and 10-20 hours or so, maybe, between Eric Huss and I (so multiply that by two).

Hristian: So this means at this point we can only focus on 2067 and 2283.

Pete: Those are settled, I suppose. TC, for the unmerged one ([Add more rules about when expressions diverge](https://github.com/rust-lang/reference/pull/2186)), should we avoid taking inspiration from them until they're merged?

TC: Everything that's there is likely more correct than the FLS.

Hristian: Do we then plan on working on 1.101 and the follow-up from this large PR at the same time?

Pete: 1.101 and the divergence items? Yes.

Pete: Let's talk about 1.100 first. We probably want to bring as much on divergence and never type into it, right? And the custom allocators. Does that make sense?

Tshepang: Is the allocator stuff relevant for the FLS?

Pete: It's a library feature, or is that also part of the language?

TC: There are lang-relevant aspects of it. In the stabilization PR, there's a [comment][TC-alloc-lang-relevance] by me summarizing the changes to the language.

[TC-alloc-lang-relevance]: https://github.com/rust-lang/rust/pull/156882#issuecomment-5422399013

Hristian (before reading the above): I have looked at this recently. I suspect that this is entirely library-related for the purposes of the FLS. The FLS doesn't talk about how allocation happens. It mentions the existence of allocated objects, but not how they're allocated. As a result, the FLS will not need to incorporate anything from [alloc: stabilize Allocator](https://github.com/rust-lang/rust/pull/156882)

Custom allocators PRs:
- stabilization report: https://github.com/rust-lang/rust/pull/156882

Hristian: I've looked, and the FLS doesn't talk about `Box`. It's a library type, and the compiler has nothing to do with `Box`.

Pete: When it comes to allocators, it seems that there's a language aspect to them, but we don't document them (heap allocation) currently in the FLS; and the library aspects don't need to be documented in the FLS because the FLS only documents the language and the compiler.

TC: `Box` looks like a library type, but it's actually a language primitive, similarly to mutable references. So it has a language invariant of uniqueness that has to be upheld by unsafe code (it's language-level, not library-level, UB to violate this). And it's `fundamental` in its generic parameter `T`. You can't write a library type that does this, so it's a language primitive.

Pete: Do we need to document this in the FLS? We can start with other things like divergence and `!` and discuss this later if we cannot come to consensus on the call now.

Hristian: By way of analogy, the FLS mentions the `Range` types because they have a special syntax. But I don't see a similar syntax for `Box`, even though it has compiler support. In that sense, we don't need to document `Box`.

TC: I don't understand. Is there something that would cause the compiler to produce a mutable reference?

Hristian: That's a good point. Wouldn't one write a borrow expresison to produce one?

TC: Sure, but that's just language syntax. They both have language-level special semantics.

Hristian: Yeah, and I'm saying there's no syntax for `Box`.

TC: That's why it looks like a library type but has the semantics of a language primitive.

Hristian: I see, because you mentioned that there are guarantees that the compiler provides.

TC: And you can't correctly document coherence if you don't talk about `Box`. (And it has special move semantics.)

Hristian: Sounds like we need to bring `Box<T>` in then. And search for other places we need to include it.

Pete: I suggest either Tshepang or Hristian put up a changelog PR and then we can split this work up.

Hristian: I can put up the changelog PR.
