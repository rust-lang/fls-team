- [Issue 716](https://github.com/rust-lang/fls/issues/716) reports a concrete consequence: the FLS currently requires pointers in constant and static initializer values to be non-dangling, but Rust accepts valid raw pointers such as `ptr::null()`, `ptr::dangling()`, and `ptr::without_provenance(...)`.
- [PR 715](https://github.com/rust-lang/fls/pull/715), implementing [issue 710](https://github.com/rust-lang/fls/issues/710), removes "indirection" terminology in favor of "pointer" terminology. This makes it important to distinguish rules about all pointer types from rules specifically about references and raw data pointers.
- The common question is: which rules apply to references, raw data pointers, function pointers, all pointer values, or provenance independently of a pointer's category?

#### Initial thoughts

- The evidence confirms that issue 716 is a real FLS defect, but replacing `pointer` with `reference` might be too broad? That replacement would also remove the existing well-formed-pointer restriction from raw pointer values.
- The smallest correction appears to be removing `non-dangling` from the affected constant and static initializer rules while retaining `well-formed pointer` for both references and raw pointers.
- A separate rule seems to still be needed for provenance in a final constant or static value that identifies an allocation deallocated during const evaluation. This isn't equivalent to the current FLS definition of `dangling`: no-provenance pointers, out-of-bounds pointers retaining live provenance, and intermediate pointers that do not survive into the final value are distinct cases.
- The FLS `dangling` definition also differs from the Rust Reference in two relevant ways: the Reference speaks about a single live allocation and says that a zero-sized pointer is never dangling, even when null.
- PR 715 might not be best treated as only a mechanical terminology replacement. If `pointer type` includes function pointers, existing FLS rules written for data pointers may accidentally acquire a wider scope, including rules based on pointed-to memory or `Deref::Target`.
