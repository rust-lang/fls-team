### Discuss the scope of numerical details wrt. the FLS

tshepang: Hristian's comment https://github.com/rust-lang/fls/pull/689#discussion_r3130663604:

> In my opinion, NaN-boxing is an implementation details, and should not be mentioned in the FLS.

> Numerical details are delegated to the corresponding primitive types, and those are currently outside the scope of the FLS.

Tshepang: I need to understand the reasoning behind this being out of scope

Hristian: The Reference mentions floating point types only in the IEEE context. It doesn't talk about NaN Boxing etc. Mention of [NaN-boxing](https://doc.rust-lang.org/stable/reference/inline-assembly.html?highlight=nan-box#r-asm.register-operands.smaller-value).

Hristian: The integer arithmetics use compiler intrinsics which go to the LLVM and that uses the platform. For f32 it's similar. I don't think the FLS should go into the semantics of integer and floating point types and operations. We could mention that floats follow IEEE standard. I don't know what's happening on hardware without f32 support. Does soft float follow IEEE?

Pete: I'm a big fan of maintaining less things. So the semantics aren't described in the Reference?

Hristian: Exactly, they're described in IEEE, why repeat them. And we do say the [right thing](https://rust-lang.github.io/fls/types-and-traits.html#floating-point-types) in the FLS. I think we're covered.

Pete: Let's get back to the PR: https://github.com/rust-lang/fls/pull/689#discussion_r3130663604

Hristian: So you're trying to define what Nan-boxing is in the Glossary. We do mention this in the inline-assembly for [RISC-V architecture](https://rust-lang.github.io/fls/inline-assembly.html#register-classes). In that case I guess we should say something.

Pete: Seems similar to [what's in the Reference](https://doc.rust-lang.org/reference/inline-assembly.html?highlight=nan-box#r-asm.register-operands.smaller-value)? The difference is that that the Rerefence has this entry in the glossary and the FLS doesn't

Pete: So this PR would put the glossary entry into the main body of the text. We define other terms we use so should we define this as well?

Tshepang: Sounds like the easiest path


### Platform details (e.g. inline assembly) for targets that are outside scope

Tshepang: "would be good also to talk about platform details, like inline assembly for targets that are outside scope"

Tshepang: This came up because of RISC-V. Which is not a qualified target. Do we get rid of RISC-V mentions? We ignore RISC-V mentiones and other targets in the release notes. But we do refer to them in the FLS now.

Hristian: I think we should get rid of the mentions for targets that are not qualified. When they become qualified, there is going to be a lot more work to handle this properly anyway

Pete: Now we have the worst of both worlds: we have the information there but it's outdated. So it won't be useful for trying to qualifying the RISC-V target. We should investigate the difference between the RISC-V in the Reference vs. the FLS. It could be a useful exercise to figure out how far away the FLS is from the Reference.

Hristian: There are only 8 subsection in the Reference that mention RISC-V. Doing the delta shouldn't be too big of an issue.

Pete: It can help us decide in a data-driven way. We might see what would it take to update the FLS to be in sync with the Reference.

Hristian: I won't have much time for FLS work until the 10th September

Tshepang: The challenge is with the consistency. We need to decide what the policy is. Why should RISC-V be special even if the diff is small. Since there's not so much in the Reference anyway, if we qualify the target, it shouldn't be that big a change. Let's carry the burden when we need to carry the burden.

Pete: Do we have anything written down in the FLS in terms of policy that describes which targets we document?

Tshepang+Hristian: No

Pete: Then we should document that.

Tshepang: I'll open a PR to do that

Pete: If we document the policy of which targets we qualify, we should remove the entries from the FLS.

Tshepang: Hristian, which targets do you care about right now?

Hristian: None. We're only looking at DO-178 library certification.

### Continuing conversation from last week: alignment with Reference

Fate of the FLS: Retire the FLS, switch Ferrous Systems to the Reference?

Hristian mentioned toning down things we overdo... would be good to know what those are.

Tshepang: When we're closing the alignment, we've overdone a few things. What are they?

Hristian: Indirection types; we invented a lot of terminology not used by the Project. We had to invent a whole section on scope and subsection on the resolution. The Reference doesn't have / explain those. But we may have gone way overboard.
