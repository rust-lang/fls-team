### [Stabilize C-variadic function definitions](https://github.com/rust-lang/fls/pull/727)

Hristian: We may have a problem with `extern function`s. As currently written, the term includes

```rust
unsafe extern "C" {
    unsafe fn foo(); // <- This
}
extern "C" bar() {}  // <- and this
```

however there are specific rules that apply to one of the flavors only. The FLS however assigns them to both flavors.

Hristian: TC, have we actually abused the term, or does `extern fn` include both flavors?

TC: Good question.

Hristian: Asking because I was trying to put some of these variadic related rules in a proper place, and there were different restrictions / flavors of external functions.

TC: (Reads.)

TC: I can find one example in the Reference of where we use it each way. But mostly the Reference avoids using the term. Mostly we talk precisely about functions with an `extern` qualifier or functions in `extern` blocks. I'd lean towards that (avoiding using ambiguous terms). The distinction here, of course, is that a function with an `extern` qualifier is a Rust function that we're externalizing. A function declaration in an `extern` block is an actual foreign function that we're creating an extern item for. If I had to pick one, functions with an `extern` qualifier are what I think of as extern functions. Highlighting the ambiguity further, when we talk about extern types (a nightly feature), those are types within an extern block.

Hristian: If I did make up a new term, a fn in an extern block would be "importing an external function". And extern fn would be exporting a function. But I don't want to make up new terms. So I'll revisit all the related rules and use the more specific language ("fn declared with .." vs. "fn declared inside of ..").

TC: We're not perfect about this in the Reference, but I do try to keep the distinction between function declarations and function definitions. A function with an `extern` qualifier is always a function definition, whereas in extern blocks you always have function declarations.

Hristian: In the FLS, we define "variadic function" as an extern function with a variadic part. But, both a function with an extern qualifier and a function declared within an extern block can have a variadic part. As a result, we lose the collective term "variadic function" as it is no longer based on constraining the term "extern function".

Hristian: Some terms in the FLS constrain others by imposing additional semantics. "Variadic function" is one of these. "Extern function" isn't appropriate, so we have to throw it out and...

TC: In the Reference, there's a similar challenge which is that there are many rules that apply in a shared way to all places where you can write a function signature, e.g., function declarations in traits and in extern blocks, function definitions (in various places), and even to function pointers.

Hristian: I've been revisiting a grammar that deals with variadic parts. Grammar for both is significantly different. For parameters of a fn pointer type you have to use an ident or underscore for the name, and for fn parameters you can have a pattern. Everything else is pretty much the same. We used to have a "plain variadic part" and a "pointer type variadic part".

TC: Yeah.

Hristian: Also can't figure out where to put th syntax for variadic part.  It's used in fn pointed types, functions. It comes into play when dealing with functions declared with the extern qualifier and within an extern block.

Hristian: I'm also trying to avoid forward references. We have types before functions.

TC: Interesting. That's not something we do in the Reference. What's the motivation for trying to avoid forward references?

Hristian: If you encounter something, the term or category should have already been explained so you have the full context. We want to tell you a story like a novel.

TC: Interesting. I think of the Reference in a similar light. It's a book and should read like a good one. Probably we just consider avoiding forward references to be a bridge too far for a technical document of this nature. We try to be good about cross-linking the first use of a term within a rule so that people can access the term easily.

Hristian: "Should be able to pick a single sentence and have enough information and cross links that you can understand it". That's why we have a lot of hyperlinks in a single sentence.

## Nominate issues instead of creating action items?

Nurzhan: Is it helpful to keep spawning action items and copying them over? Would it be nicer to nominate issues for the meeting, similarly to how lang/libs do it? I also intend to bring this up in other meetings with action items–style task management. Let me know your thoughts. TC, maybe you could talk about how these are used.

TC: In lang meetings we have to make decisions about different things that tend to come from outside the team. So we keep a nomination queue. People will nominate issues for lang, and we go through them and figure out the next step on each item to get it off our list. You can predict what will be on the agenda in the next meeting based on these labels.

TC: It depends on what you want to do in a meeting. In lang-docs, we use the nomination queue as well though the meetings are different. Things have come to us for stabilizations, etc., and we go through them and make sure we're not blocking. There's also a part where we're doing quiet detailed work.

TC: Overall, the nomination queue is helpful for making it apparent to people what's going to be on the agenda and giving structure to the meeting.

Hristian: The work that's needed to advance an item is done during the meeting?

TC: Lang is a bit like a court of appeals. People put together briefs for us with context, and we see whether we can get to a decision in a meeting (or identify what we need to ask for so that we can make a decision).

Hristian: Would that workflow make sense for us? We don't make high-level decisions. Usually we dig into PRs and resolve comments and things like that. 

TC: It's mostly a way to make it possible to autogenerate an agenda. If there's an FLS PR you want to talk about, then you label it, and when the agenda's generated, it shows up there. It makes it easy to put something on the agenda asynchronously during the week.

Hristian: And once the meeting ends, these items are reset?

TC: It's a label on GitHub, and when you no longer want to talk about it, you can take it off.

Hristian: Sounds like it will facilitate our agenda construction. Interested what Pete thinks of it. He has experience with other meetings. To me sounds like it would work.

Tshepang: It will help us structure things in advance, and that may attract more people. I don't know how exactly we'd do it.

Nurzhan: I can try setting it up for a future meeting.

TC: Looking now, I think I already created `I-fls-nominated` labels. We propagate these labels across repositories, so you could nominate an issue/PR on other repositories in the Project.
