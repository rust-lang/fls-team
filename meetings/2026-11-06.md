### "Alignment with the Reference" [fls-team#36](https://github.com/rust-lang/fls-team/issues/36)

Pete: I've not used an LLM to find the mapping as we discussed last week. I'll probably have more to show next week.

Hristian: Are you prototyping some kind of workflow or just go and do it?

Pete: The MVP is to try and map the FLS and Reference in both directions and then identify pieces of improvement. And once we've identified those, it's time to discuss what next. Maybe we could try and have a company safety qualify a piece of software based on the Reference. But that costs money and we should figure out if/what entity might be able to do that. And we should identify places from the FLS that are less covered in the Reference.

Hristian: How are you going to represent the traceability information?

Pete: I was just thinking of a huge JSON file. If you have ideas, let me know.

Hristian: Are you using anything to see whether the reference has changed? I was thinking about keeping hashes for LLMs, but then the LLM would have to read the whole thing.

Pete: I was thinking of timestamping and hashing, yes.

Hristian: So timestamped paragraphs? We could map FLS IDs to Reference IDs

TC: We call those "Reference identifiers" or, generically, "rule identifiers".

Hristian: So we'd have the map from Reference to FLS and vice versa? We'd need to track the orphan IDs somewhere.

Pete: It'd be in both directions. I feel the Reference is a much richer document, but some of the reviews I was doing for the Reference identifiers, there were items around e.g. unions that are sufficient for someone reading the Reference today, but it would need to be more formal for someone verifying the compiler etc.

Hristian: You'll also need to handle the case where a Reference rule is split across multiple FLS rules and the inverse.

Pete: Once we have this, we'll need to think about the transition plan, which way to go.  E.g. hope the FLS be as rich as the Reference, harmonize the documents. But we need to see what comes out.
